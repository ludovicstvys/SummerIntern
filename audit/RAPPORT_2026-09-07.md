# Audit du workflow Trackr — 7 septembre 2026

## Conclusion

Le parcours nominal fonctionne avec les services externes simulés, mais le workflow ne peut pas être considéré comme fiable de bout en bout. Les principaux blocages sont la configuration SMTP locale, la synchronisation Notion personnelle suspendue, la qualification des offres ouvertes et les pertes d’alertes dans plusieurs transitions. Le workflow historique peut perdre définitivement un mail après un échec SMTP.

Cet audit produit un plan de correction ; aucune correction applicative ni modification de configuration ou de production n’a été appliquée. Les changements préexistants sur `.env.example` et `.DS_Store` sont conservés.

## Défauts et plan de correction

P0 = traiter immédiatement ; P1 = fiabilité ou fonctionnalité importante ; P2 = robustesse, exploitation ou expérience utilisateur. « Reproduit » désigne un test ou une observation exécutés ; « code » désigne une conséquence identifiée par lecture du chemin concerné.

### F01 — P0 — Secrets présents dans le contexte partagé

**Preuve :** la sélection `.env` transmise contient des secrets d’application, SMTP, Notion et Vercel. Aucune valeur n’est recopiée dans le rapport. `.env` est ignoré par Git et n’est pas suivi dans l’état actuel ; cela ne prouve pas l’absence d’exposition historique.

**Correction :** révoquer/remplacer les secrets exposés chez les fournisseurs puis synchroniser les environnements concernés. Vérifier lesquels sont aussi utilisés en production. Pour `ENCRYPTION_KEY`, prévoir un rechiffrement des tokens avec l’ancienne clé avant retrait, ou une reconnexion des utilisateurs ; un remplacement aveugle rendrait les tokens existants illisibles. Révoquer les sessions/liens si nécessaire lors de la rotation applicative.

**Validation :** anciens accès révoqués, nouveaux accès fonctionnels, tokens Notion encore déchiffrables ou reconnexion explicitement proposée.

### F02 — P1 — Authentification SMTP locale cassée

**Preuve reproduite :** espaces insécables dans `SMTP_PASS_APP`, conservés par `.strip()` ; l’encodage ASCII utilisé par l’authentification SMTP échoue. Affecte `trackr_app/emailing.py:send_email` et `test.py:send_email`. Rien ne permet d’affirmer que les secrets de production contiennent la même erreur.

**Correction :** remplacer le mot de passe exposé et saisir la valeur sans séparateurs ; ajouter une validation de configuration ciblée pour le format Gmail. Conserver des diagnostics sans secret.

**Validation :** test d’encodage puis connexion SMTP et recette de réception sur une adresse de test explicitement choisie.

### F03 — P1 — Notion personnel annoncé mais non exécuté

**Preuve code/configuration :** `.github/workflows/platform-jobs.yml` ne lance pas `sync-notion` et comporte un commentaire de suspension. Le README annonce pourtant une synchronisation toutes les cinq minutes. Les identifiants OAuth locaux sont vides et `/notion/connect` renvoie alors 503 ; le dashboard propose quand même le lien.

**Correction :** décider explicitement de maintenir ou lever la suspension ; si activé, configurer OAuth et réintroduire le worker avec surveillance. Pendant la suspension, afficher l’indisponibilité et corriger la documentation.

**Validation :** OAuth → choix de page → base personnelle → insertion → mise à jour → déconnexion, dans un espace de test ; vérifier une exécution planifiée réelle.

### F04 — P1 — Échec d’invitation invisible et sans reprise

**Preuve reproduite :** `main.py:invite` crée compte, invitation et lien, commit, puis absorbe l’échec SMTP et redirige vers `/admin` sans statut. Le test `test_invitation_failure_is_visible` échoue comme attendu. Le lien expire après 15 minutes sans mécanisme d’envoi différé. Le login absorbe lui aussi l’erreur, mais son message générique protège volontairement contre l’énumération.

**Correction :** conserver un statut d’envoi d’invitation et une file avec retries ; afficher l’échec et un renvoi dans l’administration. Conserver le message public générique du login.

**Validation :** panne SMTP → statut visible → reprise → invitation reçue ; invitation répétée/concurrente sans 500 ni comptes dupliqués. La création concurrente n’est actuellement pas protégée par un upsert dans `invite`.

### F05 — P1 — Perte définitive de mails dans le workflow historique

**Preuve code :** `test.py:__main__` et les scripts régionaux synchronisent Notion puis écrivent le CSV **avant** `send_email`. Si SMTP échoue, le prochain passage ne voit plus de nouvelle offre. Si une synchronisation Notion partielle réussit puis échoue, les pages déjà créées ne figurent plus dans les créations à notifier lors du retry. `send_email` retourne aussi `False` si la configuration manque, et les appelants ignorent ce résultat.

**Correction :** utiliser une file persistante d’envois indépendante du CSV et du résultat Notion, avec un état par destinataire. Ne pas utiliser l’existence d’une page Notion comme preuve d’envoi du mail.

**Validation :** injecter une panne SMTP après sauvegarde CSV, une panne Notion après la première création et un destinataire refusé : toutes les notifications non remises restent rejouables, sans renvoi aux destinataires déjà servis.

### F06 — P1 — Collision entre régions et programmes

**Preuve réelle + reproduite :** URL partagées entre trackers ; `Offer.canonical_url` est unique, mais `region` et `programme_type` sont scalaires. `scraper.py:scrape_all` les écrase au dernier tracker. `queue_new_offer` n’est appelé qu’à la première insertion : un abonné de la seconde région peut ne recevoir aucune alerte. Test `test_shared_url_reaches_both_regions`.

**Correction :** modéliser l’offre et ses appartenances aux trackers séparément ; gérer les fermetures par source. Migrer les données et revoir l’identité utilisée pour les notifications.

**Validation :** une URL présente dans deux régions et deux programmes atteint tous les abonnés concernés, sans doublon par utilisateur ; disparition dans une seule source sans fermeture globale incorrecte.

### F07 — P1 — Offre devenue pertinente mais jamais notifiée

**Preuve reproduite :** une offre Off-cycle passe de Q2 à Q1 pour un abonné Q1 ; l’offre existante est mise à jour, mais aucun `UserOffer`/`Delivery` n’est créé. Test `test_newly_matching_offer_is_delivered`. La réouverture d’une offre existante ne déclenche pas non plus de nouvelle mise en correspondance.

**Correction :** recalculer les nouveaux utilisateurs correspondants lors des modifications et réouvertures. Définir séparément si un utilisateur déjà notifié doit recevoir une alerte de réouverture.

**Validation :** correction de trimestre, changement d’appartenance et réouverture ; aucun doublon pour les offres déjà envoyées hors politique explicite de réouverture.

### F08 — P1 — Annulation irréversible d’alertes encore non envoyées

**Preuve reproduite :** France → UK → France dans le même mode laisse la livraison France en `cancelled`. `activate_preference` ne réactive pas ce cas. La désactivation de compte annule aussi les tâches ; la réactivation du compte ne les reprend pas.

**Correction :** réconcilier les tâches annulées non envoyées lors du retour aux critères ou de la réactivation, selon une politique explicite de rattrapage. Distinguer l’historique déjà envoyé du travail annulé.

**Validation :** aller-retour de filtre et désactivation/réactivation, avec reprise des non-envoyés et préservation des envoyés.

### F09 — P2 — Dashboard trompeur après fermeture/changement de filtres

**Preuve reproduite/code :** `main.py:dashboard` affiche les 50 derniers `UserOffer`, sans filtre `is_open` ni critères courants. Le template ne signale pas les fermetures. Test `test_closed_offer_is_identified_or_hidden`.

**Correction :** séparer offres pertinentes ouvertes et historique, afficher le statut fermé, proposer pagination ou chargement des résultats suivants.

**Validation :** fermeture, changement de région et plus de 50 correspondances, avec historique clairement identifié.

### F10 — P1 — Date d’ouverture assimilée à une offre actuellement ouverte

**Preuve reproduite + réelle :** `trackr_common.py:scrape_open_programmes` exige seulement une date d’ouverture non nulle ; il ne compare pas ouverture/clôture au jour courant. Une offre clôturée en 2020 passe le test synthétique ; 223 lignes de la seconde collecte ont une clôture passée. `scrape_all` leur attribue `is_open=True`.

**Correction :** définir les règles d’ouverture avec dates et statut source, en précisant le traitement des dates inconnues et des offres rolling. Réutiliser ces règles dans les collecteurs historiques.

**Validation :** clôturée, future, ouverte, rolling et dates absentes ; contrôler les changements de jour/fuseau pertinents.

### F11 — P1 — URL externe non validée avant affichage

**Preuve reproduite :** `canonical_offer_url('javascript:alert(1)')` retourne une valeur non vide acceptée par le scraping. Les templates la placent dans `href`. L’échappement HTML ne valide pas le protocole. Aucune URL malveillante réelle n’a été observée.

**Correction :** accepter uniquement les URL HTTP(S) absolues avec hôte valide avant stockage. Pour les téléchargements historiques de descriptions, protéger également contre les destinations réseau privées et les redirections vers celles-ci.

**Validation :** rejeter `javascript:`, `data:`, les URL relatives et malformées ; tester les redirections/destinations privées pour le fetch serveur.

### F12 — P1 — Collecte vide : source en échec et anciennes offres immortelles

**Preuve :** Summer UK a échoué pendant le contrôle. Le code refuse tout snapshot vide, même si une source devient légitimement vide ; dans ce cas les anciennes offres ne peuvent jamais accumuler les deux absences nécessaires à leur fermeture.

**Correction :** distinguer réponse invalide/partielle et source vide confirmée, avec confirmations successives et métrique de fraîcheur. Diagnostiquer séparément la réponse UK avant de modifier les paramètres ou de retirer la protection.

**Validation :** deux snapshots vides autoritatifs ferment les anciennes offres ; une panne ou un vide ambigu ne les ferme pas.

### F13 — P1 — Les protections des collecteurs historiques divergent

**Preuve code :** les collecteurs France Summer/Off-cycle et UK Off-cycle dupliquent extraction/déduplication/CSV au lieu d’utiliser entièrement `trackr_common`. Ils ne contrôlent pas les métadonnées de pagination comme le collecteur partagé. Une réponse partielle non vide peut remplacer leur référence CSV. Les écritures CSV se font directement sur le fichier cible.

**Correction :** centraliser validation et déduplication, écrire vers un fichier temporaire puis remplacer atomiquement ; tester chaque script réellement lancé par le workflow.

**Validation :** réponse paginée, programme malformé, écriture interrompue, variation des paramètres de tracking : conservation de la dernière référence valide.

### F14 — P2 — Options historiques documentées mais inopérantes

**Preuve code :** `FORCE_EMAIL_ALL` élargit les candidats puis les refiltre avec les URL nouvellement créées/ouvertes dans Notion ; si aucune offre n’est nouvelle, aucun renvoi n’a lieu. `TODO_DATA_SOURCE_ID` et les fonctions TODO existent, mais `upsert_todo_for_offer` n’a aucun appel dans le workflow courant. Les changements des offres déjà présentes dans le CSV ne sont pas resynchronisés par `sync_new_offers_to_notion`.

**Correction :** préciser le contrat du workflow historique ; implémenter réellement le renvoi et la mise à jour, restaurer les TODO si souhaités, sinon retirer les options trompeuses.

**Validation :** renvoi forcé d’une offre déjà connue, modification de date d’une offre connue et création TODO si ce comportement est conservé.

### F15 — P1 — Préférences/désactivation sans effet sur les emails historiques

**Preuve code :** le workflow CSV utilise `email.csv`/variables d’environnement, indépendamment des comptes et préférences de la plateforme. `email.csv` est suivi dans Git. Un destinataire commun peut recevoir deux canaux ; désactiver son compte ne supprime pas l’envoi historique. `test.py:send_email` expose tous les destinataires dans l’en-tête `To`.

**Correction :** désigner une source unique des abonnements, migrer ou isoler explicitement le canal historique, envoyer individuellement ou en BCC ; sortir la liste du dépôt si elle ne doit pas y être conservée.

**Validation :** désabonnement/désactivation effectifs sur tous les canaux et absence d’adresses d’autres abonnés dans le mail reçu. Le chevauchement réel des destinataires n’a pas été mesuré.

### F16 — P2 — Échecs définitifs sans outil de reprise

**Preuve code :** après cinq erreurs, `Delivery` et `NotionSync` passent à `failed`. Le CLI remonte ces échecs, mais aucune interface/commande ne permet leur remise en file. Une panne fournisseur prolongée nécessite une intervention SQL. Les erreurs sont réduites au type d’exception, sans code fournisseur exploitable.

**Correction :** ajouter une reprise ciblée et auditée, des diagnostics expurgés et un délai entre tentatives adapté à la panne. Pour Notion, expliciter la reconnexion après révocation ; le refresh token stocké n’est jamais utilisé.

**Validation :** cinq échecs → correction fournisseur → reprise contrôlée ; aucune donnée sensible dans les logs. Le besoin exact de refresh automatique doit être validé contre le contrat OAuth utilisé avant implémentation.

### F17 — P2 — Création de base Notion non idempotente

**Preuve code :** chaque POST `/notion/setup` appelle la création d’une nouvelle base. Un double clic ou une répétition après timeout peut créer plusieurs bases ; les anciennes références locales sont ensuite supprimées. Les exceptions callback/création ne sont pas transformées en écran de récupération.

**Correction :** identifiant d’opération, état persistant de configuration, réutilisation/confirmation explicite avant nouvelle destination ; messages de récupération pour refus OAuth et erreurs fournisseur.

**Validation :** double soumission, timeout après création distante, refus OAuth et reconnexion sans base orpheline supplémentaire.

### F18 — P2 — Bootstrap administrateur incomplet pour un compte préexistant

**Preuve code :** `main.py:bootstrap` insère avec `on_conflict_do_nothing`. Si `ADMIN_EMAIL` correspond déjà à un abonné ou un compte désactivé, le bootstrap ne le promeut ni ne le réactive.

**Correction :** prévoir une commande explicite et contrôlée de récupération/transfert du rôle administrateur ; documenter le comportement du bootstrap.

**Validation :** premier démarrage, adresse déjà abonnée, ancien administrateur désactivé ; aucune promotion accidentelle.

### F19 — P2 — Supervision limitée et risque de famine des étapes suivantes

**Preuve code :** `/health` contrôle DB/schéma mais pas la fraîcheur du scraping ni le retard des files. Le workflow plateforme traite scraping puis mails puis digests dans un budget global de dix minutes. Les appels SMTP sont séquentiels et peuvent attendre 30 secondes chacun ; un volume élevé ou une panne peut empêcher d’atteindre les digests. Les groupes de concurrence du déploiement et des workers sont distincts.

**Correction :** horodatages de dernier succès par source/worker, métriques de retard, lots bornés et budgets par étape ; politique explicite de compatibilité workers/migrations pendant un déploiement. Mesurer avant de fixer les limites.

**Validation :** charge représentative, SMTP lent, backlog Notion et déploiement pendant un worker ; vérifier que les autres étapes continuent et que les alertes d’exploitation se déclenchent.

### F20 — P2 — Couverture de validation encore insuffisante

**Preuve :** les trois tests PostgreSQL n’ont pas été exécutés localement. Les tests actuels couvrent seulement une partie des courses possibles ; les services sortants sont simulés. Les contrôles de déploiement ne créent pas de compte et ne suivent pas une offre jusqu’à réception.

**Correction :** exécuter la CI PostgreSQL, ajouter les courses invitation/activation/scraping/désactivation, et une recette intégrée sur un environnement dédié avec destinataire et espace Notion de test. Vérifier les scripts historiques sans importer de secrets locaux : `test.py:load_env_file` ne respecte pas `PYTHON_DOTENV_DISABLED`.

**Validation :** migration réelle PostgreSQL, transactions concurrentes, panne réseau à chaque frontière et réception effective d’une notification. Ne pas interpréter un `/health` vert comme une validation de ces parcours.

## Ordre d’exécution proposé

1. **Sécuriser et rendre les blocages visibles :** F01, F02, F03, F04. Terminé lorsque les nouveaux secrets fonctionnent, qu’une invitation est reçue sur l’adresse de test et que l’état Notion affiché correspond au service réel.
2. **Fiabiliser la donnée et la mise en correspondance :** F06, F07, F08, F10, F11, F12, F13. Inclure migration des appartenances aux trackers et tests de reprise. Terminé lorsque les sept reproductions passent après retrait de leurs marqueurs `xfail`.
3. **Unifier les envois et leur reprise :** F05, F14, F15, F16. Terminé lorsqu’une panne SMTP/Notion suivie d’une relance ne perd aucune notification et que les désactivations couvrent tous les canaux.
4. **Finaliser les parcours et l’exploitation :** F09, F17, F18, F19, F20. Terminé après recette PostgreSQL et environnement de test, puis vérification des exécutions planifiées et du retard des files.

Les choix fonctionnels à fixer pendant les corrections sont le maintien du workflow historique, la réactivation de Notion personnel et la politique de rattrapage/réouverture. Ils n’empêchent pas de corriger les défauts techniques confirmés.

## Reproduire les tests

Depuis la racine du dépôt :

```sh
PYTHON_DOTENV_DISABLED=1 DATABASE_URL=sqlite:// ENVIRONMENT=development .venv/bin/python -m pytest -q
```

Les sept scénarios défectueux se trouvent dans `audit/test_workflow_20260907.py`. Leurs marqueurs `xfail(strict=True)` documentent un défaut connu : ils **ne constituent pas des tests réussis**. Pour voir les assertions échouer directement :

```sh
PYTHON_DOTENV_DISABLED=1 DATABASE_URL=sqlite:// ENVIRONMENT=development .venv/bin/python -m pytest -q audit/test_workflow_20260907.py --runxfail
```

Les tests utilisent une SQLite en mémoire et des mocks pour SMTP/Notion ; ils ne modifient pas `trackr.db`.
